# football

Searches for a team across Fotmob, Sofascore, SoccerDesk, Goal.com, and 365Scores and reports full detail on the next scheduled match from each source: kickoff time, competition, venue, weather, formations, lineups, referee, head-to-head, standings, player stats, and more — wherever each site actually makes that data available. Two supplemental sources (StadiumDB for venue capacity/history, wttr.in as a weather fallback) fill in facts none of the five per-team sources provide.

## Usage

```
npm install
npx playwright install chromium   # needed once, for the Sofascore module
npm run search -- "Liverpool"
```

## Scope and limitations

This only touches pages/endpoints each site's own `robots.txt` allows for generic bots, and doesn't attempt to defeat any anti-bot protection beyond using a real headless browser to render pages where that's required just to load the site at all (Sofascore). Two other researched sites — **Flashscore** and **Soccerway** — were deliberately excluded: their `robots.txt` blocks a long list of AI/data-mining crawlers by name (CCBot, Diffbot, AI2Bot, Bytespider, cohere-ai, etc.), an unambiguous signal not to build an AI-driven scraper against them regardless of technical bypassability. **Superscore.live** explicitly disallows `ClaudeBot` and `GPTBot` — same call. **BeSoccer** returns HTTP 406 on every request including `robots.txt` itself, even via a real browser — a hard WAF block, not attempted. **AiScore** was attempted and abandoned: its search API returns raw Protocol Buffers with no schema, and its client-side router wouldn't complete navigation to team pages even via Playwright after extensive troubleshooting — not a scope/compliance issue, just disproportionate effort for one source.

- **Fotmob** (`src/sites/fotmob.ts`) — plain HTTP GET of team/match pages; fixtures, match detail, squad, and transfers are all parsed out of the `__NEXT_DATA__` JSON already embedded in the server-rendered HTML — no `/api/` calls at all (Fotmob's `robots.txt` explicitly disallows `/api/*`). Team name → id resolution uses Fotmob's own sitemap (`sitemap/en/teams/*.xml`), cached locally to `data/fotmob-teams.json`. Its `h2h.summary` field is an undocumented 3-number array with no way to verify which number means what, so that's deliberately left out rather than guessed. No team-season card/goal totals (its `stats` field only gives per-player leaderboards via a separate `data.fotmob.com` host, out of scope).
- **Sofascore** (`src/sites/sofascore.ts`) — requires Playwright/Chromium because Cloudflare blocks non-browser clients entirely, even for fetching `robots.txt`. Sofascore's `robots.txt` (unlike Fotmob's) does not disallow `/api/`, so this module uses the same same-origin JSON endpoints the site's own pages call when rendering — venue, h2h, standings, referee career stats, and team season stats (goals/cards/possession) all come from there. Lineups/statistics 404 until the site publishes them (usually within ~1hr of kickoff), which is expected, not an error. Cloudflare's challenge response time varies a lot under repeated automated traffic, so every navigation retries up to 3 times with backoff (3s/6s/12s) before giving up, and requests within a session are paced ~800ms apart. It's also the primary **player stats** source: `/team/{id}/player-statistics/seasons` finds the team's current competition, then `/top-players/overall` for that season gives per-player goals, assists, rating, and expected goals — real names, exact match against the squad list, no cross-source guessing needed. Only the ~20-25 players with enough minutes to appear on a leaderboard are covered (fringe/youth players aren't), which is why Goal.com's stats (see below) still matter as a fallback. Also uniquely provides each team's **manager** (`homeManager`/`awayManager`: name + country, free on the same event-detail fetch) and a **manager-vs-opposing-club record** (`homeManagerVsAwayClub`/`awayManagerVsHomeClub`): NOT a true two-person head-to-head (no source tracks which matches had both current managers already in charge on both sides across their whole careers) — the honest, tractable version built instead is each manager's own W/D/L against this specific opponent club, from his last 30 matches in charge of any team (`/api/v1/manager/{id}/events/last/0`, one page, deliberately not paginated further to keep this the same "recent form" scope as everything else). One extra request per manager. `sampleSize: 0` is common and expected — most upcoming pairings simply haven't had that manager face that exact club within his last 30 games. Note: Sofascore's own manager data is occasionally stale during transfer windows (observed showing a manager still assigned to a club he'd already left) — surfaced as-is, consistent with this project's approach of trusting and reporting source data rather than second-guessing it.
- **SoccerDesk** (`src/sites/soccerdesk.ts`) — no browser needed at all; plain `fetch` works throughout. Team search hits `api.soccerdesk.com`, which has no `robots.txt` at all (a 404) — per RFC 9309 that means no crawling restrictions apply. `www.soccerdesk.com`'s `robots.txt` has only a broken, unfilled template rule (`Disallow: /[sport]/*`, matching no real URL) plus a blanket `Allow: /`. No venue/referee/attendance/weather/match-stats anywhere in its UI — confirmed by checking the actual match page (only Info/Lineups/H2H tabs exist). In exchange, it uniquely provides per-match `injured`/`suspended` player lists that neither other source has.
- **Goal.com** (`src/sites/goal.ts`) — plain HTTP GET, `robots.txt` is a blanket `Allow: /`. Team name → id resolution uses `sitemap/teams.xml` (~555 entries — solid for major clubs, but many smaller/non-European clubs like Corinthians aren't listed, a real coverage gap rather than a matching bug). One of the richest sources per match: venue, half-time score, full match stats (xG, possession, shots, passes, cards), goal-scorer+assist timeline, formations, and labeled head-to-head stats. `referee` is consistently an empty array on every match checked (friendlies and competitive fixtures alike) — genuinely unpopulated by this source, not a fetch failure. Squad data has season per-player stats (appearances/goals/assists/cards) but no injuries/age/market value/transfers — used as the **player stats** fallback for players Sofascore's top-players leaderboard doesn't cover. Goal.com abbreviates first names ("A. Becker"), so this fallback matches by surname only (`search.ts`'s `enrichSquadWithSeasonStats`), a real approximation: two same-surname players in one squad would collide.
- **365Scores** (`src/sites/365scores.ts`) — no browser needed; plain `fetch` works throughout, including against the actual data API host `webws.365scores.com`, which has no `robots.txt` at all (a 404, so no restrictions per RFC 9309). The main site's `robots.txt` has no `/api/`-equivalent disallow either, and explicitly allows team pages. Team search, recent results (`competitors/recentForm`), upcoming fixtures (`games/current`), full match detail (venue, referee, attendance, lineups with formation and named positions, goal/substitution timeline), standings, and squad (with age/position/height already included per player) all confirmed working. No match stats (possession/shots) or head-to-head endpoint was found within reasonable research effort, so those stay `null` rather than being guessed at.

Two more sources supplement the report but aren't full per-team sources (no fixtures/lineups/squad search of their own) — they only ever fill a couple of specific fields, fetched once after the merge instead of once per source:

- **StadiumDB** (`src/sites/stadiumdb.ts`) — venue capacity, year opened, and renovation years. `robots.txt` only disallows `/lay-gfx/`, no AI-bot blocks. No sitemap or search endpoint exists, so team → stadium resolution goes through the site's own browse structure: `/stadiums` (country code index, fetched once and cached to `data/stadiumdb-countries.json`) → `/stadiums/{code}` (every stadium in that country with a "Clubs" column, one page, no pagination even for England's 125 entries) → the stadium's own detail page. Matches by **club name** (from that "Clubs" column), not venue name — more reliable than matching sponsor-renamed venue strings ("Etihad Stadium" vs "City of Manchester Stadium") across sources. Tries the home club first, then the away club, so neutral-venue matches (pre-season friendlies at a rented stadium) correctly resolve to nothing instead of a wrong guess. One real bug caught during testing: some rows' "Clubs" field is a literal `"-"` (no club plays there — motor speedways, athletics venues, StadiumDB isn't football-only), and naively substring-matching against a normalized empty string matches *everything* in JavaScript (`"anything".includes("")` is `true`) — fixed by dropping `"-"` rows before matching, plus a 4-character floor on the fuzzy match.
- **wttr.in** (`src/sites/wttrin.ts`) — weather fallback for matches Fotmob doesn't have a forecast for yet. AccuWeather was tried first and ruled out: hard Akamai WAF block (403 on `robots.txt` itself, `ERR_HTTP2_PROTOCOL_ERROR` even via a real headless Playwright browser — same class of block as fbref, not something normal browser rendering gets past). wttr.in has no dedicated `/robots.txt` at all — every path, including `/robots.txt` itself, is treated as a location query and 500s with "location not found" — so per RFC 9309 no crawling restriction applies, and it's explicitly built for exactly this kind of plain-HTTP programmatic access (`curl wttr.in/City`, no API key). Only forecasts 3 days out. Reports the match day's **midday local conditions** as a same-day approximation rather than an exact kickoff-hour forecast, since reconciling wttr.in's location-local hourly buckets against a UTC kickoff time isn't worth the complexity for a 3-day-out forecast anyway.
- **Squawka** (`src/sites/squawka.ts`) — per-player defensive activity counts (`defensiveStats`: tackles made, interceptions, ball recoveries, clearances), shown as a "Top defenders" line alongside the existing top scorers/assists. Clean `robots.txt` (only `/wp-admin/` and `/cdn-cgi/*` disallowed, no AI-bot blocks). Requires Playwright: the real data endpoint (`/wp-json/vcsw/v2/statistics`) needs an `X-WP-Nonce` header that only ever exists embedded in a page's own server-rendered HTML (`<script id="swp--common-block-args">`) — that's a normal CSRF token any visitor's browser already has, not a bypass of anything the site disallows. Two real bugs caught during development, both about picking the wrong data slice rather than a fetch failure: (1) the upcoming match's own competition (often a friendly or cup tie) was being passed to Squawka directly, which obviously isn't a league it tracks, silently returning nothing — fixed by trying each of the team's own *recent* competitions (`form.recentCompetitions`) in order instead; (2) picking "most recent start_date" among same-named competition entries picked next season's not-yet-started entry (a "Premier League 2026/27" row existed with zero underlying stats) over the just-finished season that actually has data — fixed by filtering to seasons whose `start_date` has already passed. Coverage skews English/European top leagues (Premier League, Championship, League One/Two, Bundesliga, Ligue 1, Serie A) plus MLS and various qualifiers/AFCON — confirmed no Brasileirão, so South American clubs like Corinthians correctly get no data here rather than a wrong guess. Also worth noting since it very nearly got reported wrong: "Errors Leading to Goals", "Pressures", and "PPDA" are all *listed* as selectable stat-filter options on Squawka but return **zero actual items** when queried, in every competition checked — a selectable option existing doesn't mean the data behind it exists. Those three, and genuine defensive-line-height data, remain unavailable from any source found so far.

Each site's actual Terms of Service may still restrict automated data collection/reuse beyond what `robots.txt` covers — review those before using this for anything beyond personal/exploratory use.

Kickoff times can genuinely differ by an hour or so between sources for not-yet-finalized fixtures (seen with pre-season friendlies) — that's a real data discrepancy between providers, not a bug. Venue, referee, standings, and head-to-head data matching (or closely agreeing) across independently-scraped sources is a good sanity check that all five are reporting real data — this cross-validation caught at least one real bug during development (Fotmob's fixture list encodes unplayed matches with `score: 0` instead of `null`, which briefly produced fake "0-0" results in computed form stats before being fixed).

### Team-name matching (`src/teamNameMatch.ts`)

Every source resolves a searched/opponent team name to its own internal id independently, and their naming conventions don't always agree with Sofascore's official name (the name this tool actually searches other sources with, for the opponent side). Two concrete, repeatedly-observed mismatch shapes, both fixed with explicit, mechanical, documented transformations rather than a hardcoded per-team alias table (so the fix generalizes beyond the specific teams caught in testing):

- **Diacritics** — "Almería" vs Fotmob/Goal.com's slug/SoccerDesk's search index "Almeria". Every source's `normalize()`/`slugify()` used to only strip non-`[a-z0-9]` characters, which turns "í" into a space rather than "i", corrupting the match instead of making it. Fixed by stripping combining diacritical marks (Unicode NFD decomposition) before that.
- **Generic club-entity suffixes** — "Girona FC" vs Fotmob/Goal.com's slug "girona" / SoccerDesk's indexed name "Girona". Fotmob and Goal.com's local team indexes now also try the reverse-direction substring match (query contains the slug, not just the other way around) with a 4-character floor to avoid a generic short slug false-matching an unrelated longer query — same convention as StadiumDB's existing fuzzy-match floor. SoccerDesk and 365Scores hit a live search API by query string instead of a local index, so for those two, a failed exact-name query is retried with the diacritics-stripped and then generic-suffix-stripped variants of the name until one returns results.

Confirmed fixed live: searching "Arsenal" (next opponent: Girona FC) previously produced `opponent lookup issue: No Fotmob team found matching "Girona FC"; No SoccerDesk team found matching "Girona FC"; No Goal.com team found matching "Girona FC"` and left the opponent's side of xG/possession-matchup null; after this fix, all three resolve Girona FC correctly and the opponent's xG estimate populates from real data.

## Report merging

Every report is built with **Sofascore as the base source** — its data is used for every field where available, and the other four sources (Fotmob, SoccerDesk, Goal.com, 365Scores) only fill in fields Sofascore is missing (e.g. weather, since Sofascore doesn't have that field at all). Every filled-in field is tagged `(via <source>)` in the output so it's clear where each piece of data actually came from.

Both teams' form (`form` and `opponentForm` in the JSON output) are printed as symmetric sections — last 5/last 10, streak, momentum, half split, narrow wins, scoring draws, and BTTS all computed identically for both sides. `opponentForm` was already being computed internally (several insights need it — rank record, resilience, fatigue flag, home advantage, streak stability), just never actually shown; it's now its own section right after the searched team's form, not just a byproduct sitting unused in memory.

## Insights (rule-based)

Beyond the raw merged data, `search.ts` computes a small set of derived stats and classifications from data already fetched — plus two categories that needed genuinely new requests:

- **Half-time split** (`halfSplit`) — aggregates Sofascore's own half-time scores (`homeScoreHT`/`awayScoreHT`, already present in its fixture list) across the recent form sample, showing whether a team scores/concedes more before or after the break.
- **Current streak, home/away win rate, momentum, narrow-win share** — pure computation over the already-fetched fixture list. Momentum trend requires a ≥0.5 points-per-game swing (last 3 vs prior 3) to call "improving"/"declining"; smaller swings are "stable" rather than asserting a trend from noise.
- **Missing midfielders** — cross-references the merged injuries list against each player's role/position field (handles Fotmob's "Midfielder", Sofascore's "M", Goal's "MIDFIELDER", 365Scores' "Midfielder").
- **Season xG estimate** (`homeXgEstimate`/`awayXgEstimate`) — no source publishes a season-aggregate xG figure (checked twice, conclusively absent), so this is built by re-fetching match detail for the last 5 *finished* Fotmob matches (Fotmob's own per-match `matchStats` includes "Expected goals (xG)") and summing. Combined with Sofascore's per-player `expectedGoals` (see player stats above), this is the intended answer for "expected goals" — no source anywhere publishes a pre-match xG *projection* for a specific not-yet-played fixture, so this is season-aggregate form, not a prediction for the upcoming game. Computed for **both teams**: the searched team's side reuses the fixture list already fetched elsewhere (5 detail requests, as before); the opponent's side needs its own Fotmob fixture list, which nothing else in this tool fetches, so that's +1 team-fixtures request and +5 match-detail requests, newly added for the opponent specifically. `null` when a team's last 5 finished matches don't have the xG stat published — genuinely common in the current pre-season window, since friendlies don't get full stats coverage on Fotmob, confirmed by direct testing (Real Betis's last 5 "finished" Fotmob matches were all summer friendlies with zero `matchStats` entries) rather than a bug.
- **Opponent profile** — until this point, only the searched team's own data was ever fetched. The opponent now gets the exact same multi-source profile treatment as the searched team (all 5 sources fetched and merged with `mergeTeamProfile`, same Sofascore-base-plus-gap-fill logic, same player stats) — both teams' squads, injuries, transfers, and top scorers/assists are always scraped, not just one side. Only the "rest days" fixture-list lookup stays single-source (against the merged match's base source), since that's a single number with nothing to merge. "Which team is more rested" and "which squad is more experienced" (`insights.restComparison`/`experienceComparison`) are computed from this. This roughly doubles the total number of requests a run makes (up to 5 more profile fetches, one per source); Sofascore's own pacing/retry logic (~800ms between calls, 3 retries with backoff) already accounts for sustained sequential load, so this doesn't change the compliance posture, just the runtime.
- **Standings zone** (`homeStandingsZone`/`awayStandingsZone`) — position ≤ 4 → `top-of-table`, position > totalTeams − 3 → `relegation-zone`, else `midtable`. This is a **fixed positional rule, not tuned per competition** — most leagues don't use exactly 4 continental qualification spots or exactly 3 relegation spots, so treat it as an approximation, not that competition's actual rules.
- **Card discipline** (`homeCardDiscipline`/`awayCardDiscipline`) — yellow/red cards per game from the season totals. `elevatedRisk` flags at >2.5 yellow/game or >0.2 red/game; a typical top-division team runs ~1.8–2.2 yellows/game, so this is a deliberately conservative "notably above average" cutoff, not a league-specific benchmark.
- **Experience comparison** — "more experienced" requires a ≥1.5-year average-age gap between the two squads; smaller gaps are called "even".
- **Travel** (`travelInfo`) — each team's own registered country (Sofascore only, free on the same event fetch) compared against the match venue's country, plus a rough distance in km. Every free geocoding service checked (Nominatim, Photon/Komoot, geocode.maps.co) explicitly disallows its search endpoint in `robots.txt` — even Nominatim's own separate usage policy claims to permit rate-limited API use, but the robots.txt itself blocks it, and this project has held the line on explicit disallows throughout (same call as never using Fotmob's disallowed `/api/`). So distance comes from `src/geo.ts`, a small static table of capital-city coordinates shipped in the code (no live requests, no compliance question) — the km figure is a **country-level** approximation (capital-to-capital great-circle), not venue-to-venue precision.
- **Opponent rank record** (`homeOpponentRankRecord`/`awayOpponentRankRecord`) — each team's W/D/L record specifically against opponents **currently** ranked higher in the same competition as the upcoming match. "Currently," not at the time of that result, is the real caveat — no source publishes point-in-time historical standings, so a team that's since fallen down the table still counts as "higher-ranked" here. Only counts results within the same competition as the upcoming match (cross-competition rank isn't comparable — a Champions League mid-table side can be a domestic league leader). Costs zero extra requests: the full standings table was already being fetched and discarded down to just the two teams in the match, so every opponent's current rank was sitting in a payload we already had.
- **Availability / presence** (`homePresence`/`awayPresence`) — a Present/Absent flag per squad member (Absent = on the injuries list) plus whether they're in this match's confirmed/predicted starting XI. Doesn't distinguish "fit but not selected" from "on the bench," since no source publishes a separate bench list.
- **Rotation** (`homeRotation`/`awayRotation`) — starting-XI changes between each team's **last two played matches**, not a diff against the upcoming match's own lineup, since that's usually unpublished until close to kickoff and would leave this null for most searches. Reads as a general rotation tendency, not "how much will they rotate for this specific game." Costs 2 extra `details()` fetches per team (4 total), sequential to respect Sofascore's pacing — this is the most expensive of the newer insights and adds real runtime to every search.
- **Resilience** (`homeResilience`/`awayResilience`) — among a team's recent results that weren't wins, what share were draws rather than losses. A team with a high draw share here tends to grind out a point when not winning outright, rather than collapsing into a loss — the objective version of "a struggling team may still manage a point."
- **Performance by rest** (`homeRestPerformance`/`awayRestPerformance`) — points-per-game split by how much rest the team had before that match (≤3 days = "short," same threshold used elsewhere for "tight schedule"), computed across every played match on record rather than just the recent-form sample so each bucket has a real sample size.
- **Experience/H2H alignment** (`experienceH2H`) — whether the more experienced squad (by average age) also happens to hold the head-to-head record between these two specific teams. Correlation only — doesn't claim age causes the h2h record, just reports whether the two line up. `null` (not "even") when either side is itself even, since "aligned with an even thing" isn't a meaningful comparison.
- **Fatigue flag** (`homeFatigueFlag`/`awayFatigueFlag`) — flags "juggling multiple competitions on a tight schedule" only when **both** conditions hold: more than one distinct competition in the recent-form sample, AND an average gap under 5 days between the last three matches. Either signal alone isn't flagged — a team can handle multiple competitions fine with normal rest, or a tight schedule fine within one competition; it's the combination being checked for.
- **Home advantage** (`homeAdvantage`/`awayAdvantage`) — each team's own home-win-rate minus away-win-rate gap (all played matches on record). ≥20pp = "strong", 5-20pp = "slight", -5 to 5pp = "negligible", ≤-5pp = "reverse" (the team genuinely does worse at home than away — a real, if less common, pattern).
- **Streak stability** (`homeStreakStability`/`awayStreakStability`) — combines the current streak with rotation: "stable" requires **both** a winning streak of 2+ games AND 2 or fewer XI changes between the last two matches. Only evaluated for winning streaks; drawing/losing streaks just report the streak itself.
- **Losing-streak xG context** (`homeLosingStreakContext`/`awayLosingStreakContext`) — combines a losing streak (2+ games) with the season xG estimate: flagged as a potential turnaround when actual goals scored are at least 1 below expected goals, i.e. the team is creating enough to have scored more than they have. This is the data-backed version of "may unexpectedly break the pattern," not a prediction. Computed for both teams, each against their own xG estimate — no extra requests beyond what `homeXgEstimate`/`awayXgEstimate` already pays for.
- **Competition-specific stakes** (extends `StandingsZoneInfo`) — the top-4/bottom-3 rule is now the *fallback*, not the default: `search.ts`'s `LEAGUE_STAKES` table has the real continental/relegation spot counts for major leagues matched against Sofascore's exact competition name string (Premier League, La Liga, Serie A, Bundesliga, Ligue 1, Brasileirão Betano, Primeira Liga, Eredivisie). Also adds `pointsFromBoundary` — how many points separate this team from the nearer zone edge (using the full standings table's points, Sofascore-only) — and `inTheMix` (≤6 points = genuinely still contesting that zone, not just occupying a position near it on paper).
- **Structured suspensions** — SoccerDesk's per-match suspended-player lists (previously only ever surfaced as free text inside a note) are now real fields (`homeSuspendedPlayers`/`awaySuspendedPlayers`) and get merged into presence (`homePresence`/`awayPresence`) alongside injuries, so "missing key players due to injuries **or suspensions**" is one unified P/A view instead of two separate things a reader had to combine themselves.
- **Card/sending-off risk** (`homeCardRisks`/`awayCardRisks`) — flags players from per-player season card totals already fetched (`SeasonPlayerStats`): `accumulationRisk` at ≥4 season yellows (a generic "one booking from a ban" early-warning — many leagues suspend at 5 accumulated yellows, but the exact trigger varies by competition and we don't have that rule data, so 4 is deliberately generic, not competition-tuned), and `priorDismissal` at ≥1 red card already this season. Only lists players who are actually flagged, sorted worst-first, not the full squad.
- **Narrow win / scoring draw / BTTS** (`FormSummary.narrowWinSharePct`/`scoringDrawSharePct`/`bttsSharePct`) — "narrow win" was redefined from "any 1-goal margin" (which also counted high-scoring games like 4-3) to genuinely tight and low-scoring: a 1-goal margin **and** 3 total goals or fewer (1-0, 2-1). Two companion stats, both from the last 10 played matches' scorelines directly, independent of W/D/L: the share of draws that weren't 0-0 ("found the net despite not winning," pairing with the resilience stat above), and the share of matches (any result) where both sides scored (BTTS).
- **Rotation shape diff** (extends `RotationInfo`) — alongside the existing player-identity diff, now also compares formation between the same two matches (`lastFormation`/`previousFormation`/`formationChanged`) and defender count, parsed from the formation string's leading number (`"4-3-3"` → 4) rather than counting each player's own position field, since position-code formats are inconsistent across sources while the formation string is already normalized. No new requests — same two already-fetched match details.
- **Defensive duel vulnerability** (`homeDuelVulnerabilities`/`awayDuelVulnerabilities`) — Squawka again: defenders (by role) whose `groundDuelSuccessPct` is below 50%, i.e. losing more ground duels than winning. "Duels Lost" itself returns zero items on Squawka (same empty-option trap as Errors/Pressures/PPDA — see below), but `Ground Duel Success %` has real data and answers the same question more directly.
- **Possession matchup** (`homePossessionMatchup`/`awayPossessionMatchup`) — points-per-game split by whether the opponent had ≥55% possession, from each team's own last 5 played matches with a Goal.com possession stat available (the one source with reliable per-match possession). Computed for both teams, same shape as the xG estimate above: the searched team's side reuses an already-fetched fixture list, the opponent's side needs +1 Goal.com team-fixtures request and +5 Goal.com match-detail requests, newly added.
- **Rotation, with context** (extends `RotationInfo`) — the player-identity and formation diff now also carries `precedingResult`: the team's own result (W/D/L) in the *older* of the two matches being compared, i.e. what happened right before the changes shown were made. Answers "did they change things after a loss" directly off the same two already-fetched matches — no separate historical-pattern computation, which would've meant fetching lineups for many more past matches just to build an "average rotation after a loss" sample.
- **Attacking-defender exposure** (`homeFullbackExposure`/`awayFullbackExposure`) — defenders with above-*their-own-team's-median* Squawka `chancesCreated` **and** below-55% `groundDuelSuccessPct`: genuinely attacking (by their own squad's standard, not a fixed league-wide number, since "high" creativity means different things at different clubs) but below-average defensively. The direct answer to "teams that rely on attacking full-backs can be exposed defensively." Can't reliably separate centre-backs from full-backs across sources (role fields are inconsistent — just "D" or "DEFENDER", no LB/RB/CB granularity), so this covers all defenders who clear both bars, not full-backs specifically. Three other creativity stats were tried first and all returned zero items on Squawka (the same empty-option trap as Errors/Pressures/PPDA) — "Accurate Crosses", "Key Passes", "Final Third Entries" are all listed as selectable but have no real data behind them; "Chances Created" is the one that does.
- **New standing / standings impact** (`homeStandingsImpact`/`awayStandingsImpact`) — what rank this team would hold if the upcoming match ends in a win/draw/loss. Applies the standard 3/1/0 points for that outcome to both teams' current points, then re-ranks against the full standings table (Sofascore only, same table `pointsFromBoundary` uses above). Matches each team to its table row by **position**, not name — both teams' current positions are already reliably resolved via ID-based matching upstream, so this sidesteps the fuzzy-name-matching bug class that bit StadiumDB earlier (a short or oddly-formatted name silently matching the wrong row). Ties after the simulated result are broken by keeping the original relative order, since the table doesn't carry goal difference — a real approximation for two teams level on points after the hypothetical result. `null` whenever the upcoming match's competition has no standings table (friendlies, cups, and anything else outside Sofascore's league coverage).
- **Referee × card-risk cross-reference** (`refereeCardRiskNote`) — pure synthesis of two things already fetched separately: the match referee's own season card rate (`refereeStats`) and each team's already-flagged card-risk players (`homeCardRisks`/`awayCardRisks`). No new requests. Reuses the same >2.5 yellow/game "elevated" threshold as `CardDisciplineInfo`, applied to the referee instead of a team. `null` whenever there's nothing to cross-reference — no referee stats published yet (common for not-yet-finalized pre-season fixtures), or neither team has any flagged players.
- **Data completeness footer** — a per-run `X/Y fields populated` count over the merged match-detail and insights schema (excluding bookkeeping/identity fields like `sourceUrl`/`status`/`fieldSources` that are never meaningfully null). Coverage genuinely swings a lot run to run — pre-season friendlies routinely lack referees/standings/full match stats, competitive fixtures usually don't — so this is a signal for *that specific run*, not a fixed target to hit. Confirmed live: a competitive Corinthians league fixture came back 55/74.
- **Season shots estimate** (`homeShotsEstimate`/`awayShotsEstimate`) — same shape and scope as the season xG estimate (last 5 finished Fotmob matches), but for `"Total shots"`/`"Shots on target"` (confirmed field names). Genuinely free: `computeSeasonMatchStatsEstimate` fetches those same 5 Fotmob match details once and derives xG, shots, *and* the card-discipline venue split below from that single loop, rather than fetching the same pages three separate times.
- **Season corners estimate** (`homeCornersEstimate`/`awayCornersEstimate`) — same free-add relationship to the possession matchup: `computePossessionMatchup` already fetches the last 5 finished Goal.com match details for the possession stat, and Goal.com's `"Corner total"` (confirmed field name) comes along in the same payload.
- **Clean sheet / scoreless streaks** (`FormSummary.cleanSheetStreak`/`scorelessStreak`) — longest run of consecutive most-recent played matches with zero goals conceded / zero goals scored, same "run from the most recent match" shape as `currentStreak`, just a different condition. Pure computation over the fixture list already fetched, no new requests. Verified against synthetic data (a 3-game clean-sheet run correctly breaking on a conceded goal) since no live team searched during testing happened to have a 2+ run at the time. Only printed at 2+ games (a 1-game "streak" isn't a notable signal), though the raw count (including 0) is always in the JSON.
- **Card discipline by venue** (`homeCardDisciplineVenueSplit`/`awayCardDisciplineVenueSplit`) — splits a team's own card discipline by whether *they* were at home or away, not to be confused with which side of the upcoming match they're on. Also derived for free from the same Fotmob match-detail fetch as the shots/xG estimates above (`"Yellow cards"`/`"Red cards"`), so despite originally looking like it would need its own new requests, reusing that existing loop made it free too. One real, confirmed-live data-quality caveat: Fotmob's `"Yellow cards"` stat came back `0-0` for all of Corinthians' and Internacional's last 5 matches checked (cross-checked against Arsenal's matches in the same run, which had real non-zero counts, confirming this isn't a parsing bug) — Fotmob's per-match card stat coverage appears to be thinner for at least some Brasileirão fixtures, the same kind of South-American-coverage gap already noted elsewhere in this README (e.g. Squawka's Brasileirão gap). Either venue side can also be `null`/`0` sample if all 5 of a team's recent matches happened to be on one side.
- **Season aerial duels estimate** (`homeAerialEstimate`/`awayAerialEstimate`) — another free addition to the same `computeSeasonMatchStatsEstimate` loop: Fotmob's `"Aerial duels won"` stat is a `"count (%)"` string (e.g. `"21 (58%)"`), parsed with a leading-integer parse (`parseLeadingInt`) rather than `Number()`, which would just return `NaN` on that format.
- **Season big chances estimate** (`homeBigChancesEstimate`/`awayBigChancesEstimate`) — created/missed big chances, for and against, from the same loop and Fotmob's `"Big chances"`/`"Big chances missed"` fields (plain integers, no parsing gotcha). A chance-quality signal distinct from raw shot volume — a team can out-shoot an opponent while creating fewer genuinely clear-cut chances.
- **Season passing style** (`homePassingStyle`/`awayPassingStyle`) — pass accuracy % and long-ball share, each team's own build-up profile rather than a for/against contrast (see the type's doc comment for why). Same free loop, using `"Passes"`, `"Accurate passes"`, and `"Accurate long balls"`. One real gotcha caught during testing and fixed: Fotmob's `"Passes"` stat name appears **twice** in the raw stats array — the first occurrence has empty `home`/`away` strings (an apparent placeholder/header row) and the second has the real total, so a naive `.find()` would have silently picked up the empty one; the fix explicitly filters for a non-empty value. Verified by hand-computing all three stats (pass accuracy, long-ball share, aerial duels, big chances) directly from Fotmob's raw match data for Arsenal's last 5 matches and confirming an exact match against the tool's own output (83.8% pass accuracy, 4.9% long-ball share, 67/69 aerial duels, 14/11 big chances/missed — all matched exactly).
- **Season fouls estimate** (`homeFoulsEstimate`/`awayFoulsEstimate`) — another free addition to the same loop, from Fotmob's `"Fouls committed"` (plain integers). Meant to pair with the referee × card-risk cross-reference above: a team that fouls a lot in front of a card-happy referee is a stronger signal than either fact reported alone (not combined into one field, since they're independently useful and computed at different points in the pipeline). Hand-verified against Arsenal's last 5 matches (58 committed / 63 suffered, exact match).
- **Set-piece threat flag** (`homeSetPieceThreat`/`awaySetPieceThreat`) — pure synthesis, zero new requests: cross-references a team's own corners-won rate (`SeasonCornersEstimate`, Goal.com) against the *specific upcoming opponent's* own aerial-duel win rate (`SeasonAerialEstimate`, Fotmob), both already fetched independently for each side. `elevated` requires **both** ≥5 corners/game (deliberately round, not competition-tuned) **and** the opponent's own aerial win rate below 50% (losing more of their own aerial duels than they win). `null` whenever the team's own corners estimate is null (e.g. Goal.com doesn't have a `"Corner total"` stat for that team's recent matches) — a real, expected gap, not a bug (confirmed live: Girona FC's corners came back null in testing, correctly nulling its set-piece-threat flag while its direct-play-exposure flag below still computed fine, since that one depends on Fotmob passing data instead).
- **Direct-play exposure flag** (`homeDirectPlayExposure`/`awayDirectPlayExposure`) — same cross-reference shape and opponent-aerial signal as the set-piece flag, but paired with the team's own long-ball share (`SeasonPassingStyleEstimate`, Fotmob) instead of corners. `elevated` requires **both** ≥15% long-ball share (deliberately round) **and** the opponent's aerial win rate below 50%.
- **Season goalkeeping estimate** (`homeGoalkeepingEstimate`/`awayGoalkeepingEstimate`) — the last clean addition from Fotmob's per-match stats before that field is fully mined out: `"Keeper saves"` (plain integer), with `savePct` computed against the shots-on-target-faced figure already parsed for the shots estimate in the same match (not a separate stat lookup), so a match only counts toward this estimate when both are present together. Hand-verified against Arsenal's last 5 matches (10 saves on 12 shots faced, 83.3% save rate, 6 conceded — exact match against the tool's own output).
- **Season defensive errors estimate** (`homeDefensiveErrorsEstimate`/`awayDefensiveErrorsEstimate`) — Goal.com's `"Defensive error"` stat, free addition to the same loop already made for possession/corners. Checked specifically to distinguish it from the empty-option-trap class of stat (Squawka's "Errors Leading to Goals" is *listed* but returns zero items on every query) — this one is genuinely different: when present it has real non-zero counts, Goal.com just doesn't publish it for every match (confirmed live: present in 2 of 8 Arsenal matches checked, absent — not zero — in the rest), so its sample size runs noticeably smaller than the other Goal.com-derived estimates from the same loop. Hand-verified against the 2 matches that had it (3 for / 7 against, exact match).

**Researched and ruled out: venue-specific head-to-head.** The idea was narrowing the H2H record to matches actually played at the upcoming venue, not all-time. Sofascore's `/api/v1/event/{id}/h2h` endpoint — the only H2H data this project uses — only returns an aggregate `teamDuel` tally (`homeWins`/`awayWins`/`draws`) and a `managerDuel` field, confirmed `null` on a live check; there's no per-match list with venue (or date) attached, and no separate endpoint for one was found (`/h2h/events`, `/duel` both 404). Building this properly would mean paginating each team's own multi-season event history looking for meetings at a specific ground, which is a much larger scope (and likely a tiny sample — most head-to-head venue meetings are just the season's home leg) than "cross-reference two numbers already fetched," so it's staying out rather than being approximated.

Everything phrased in the original checklist as "teams that tend to / may / often..." (home advantage psychology, complacency, favorite/underdog pressure, tactical counter-play) stays out of scope on principle — that's narrative judgment layered on top of these numbers, not something a fixed rule can honestly claim to compute. The `Insights` section only reports things with a stated, checkable definition.

One item from the original checklist is **not obtainable from any source found so far**: pressing intensity (PPDA-style metrics). This needs either optical player-tracking data (which vendors like Opta Vision, StatsBomb, and SkillCorner sell directly to clubs and broadcasters, not published free anywhere) or a named "Pressures"/"PPDA" stat, which — confirmed by direct testing — Squawka lists as a selectable filter option but returns **zero actual items** for, in every competition checked (same empty-option trap that also ruled out "Errors Leading to Goals" as a literal metric, though a real proxy for that one exists via duel success rate above). Understat.com (the most likely public source) blocks all crawling (`robots.txt: Disallow: /`); WhoScored.com has a permissive `robots.txt` and loads fine via a real browser, but its team-search mechanism wasn't found after real effort (no sitemap, search interaction buried under dozens of ad-exchange tracking calls) — technically promising but not pursued further given the effort-to-value ratio, similar to the earlier AiScore decision.

A team-level "Offsides" stat also exists on Squawka and was tempting as a defensive-line-height proxy (a high line catches more attackers offside), but it was **not used**: the same stat name at player level is clearly a forward's own times-caught-offside count (an attacking stat, the opposite of what's wanted), and there's no way to confirm the team-level number means "opponents caught offside against this team" rather than just the sum of the team's own players' offside counts. Rather than guess at a stat's meaning the way "Errors Leading to Goals" turned out to be a trap, this was left out. Defensive line height and attacking full-back exposure no longer have *no* data, though — Squawka's defensive-activity stats (tackles, interceptions, recoveries, clearances, ground duel success) are a real, if imperfect, proxy for the former, and the `FullbackExposureInfo` rule above (creativity vs. defensive activity, relative to each team's own defenders) is a genuine, more direct answer for the latter.

Two more items are flagged as **not built**, for different reasons than the pressing/PPDA case above: pitch/surface quality has no data behind it on any of the 7 sources this project uses — nobody checked publishes it, and no proxy was found either (unlike defensive line height, there's no adjacent stat that gets at the same idea). "Who scores first gains a psychological advantage" would need per-match goal-timing data (which minute each side's first goal came) across many historical matches to compute properly, not just the next match's own timeline — that means fetching full match details (lineups, events) for a much larger sample than the 2-5 matches other lookback features already pay for, and wasn't judged worth the added runtime for a narrative claim rather than a hard fact.

## Dropped: Livescore

Livescore was removed. It has no crawlable, non-API team search — name → id resolution only worked for a handful of clubs in its "popular teams" nav, and venue/referee/lineups weren't server-rendered anywhere on the site (even the match page's default "Info" tab only shipped label strings, not values), so it added a source that was both hard to search and thin on data without crossing into its disallowed `/api/*`.

## Researched and ruled out: player/venue/weather bonus-data candidates

- **Transfermarkt** and **Sofifa** — both explicitly name `ClaudeBot` in `robots.txt` with `Disallow: /` (plus GPTBot, CCBot, and others). Same hard non-consent signal as Superscore.live — not attempted regardless of technical feasibility.
- **africa.espn.com** — blocks GPTBot and Google-Extended outright, and separately, its general `User-agent: *` rules explicitly disallow the exact paths that would matter here: `/football/matchstats`, `/football/lineups`, `/football/commentary`, `/soccer/matchstats`, `/soccer/lineups`, `/soccer/commentary` — not just an AI-crawler issue, the valuable data is off-limits to every bot.
- **fbref.com** — `robots.txt` itself returns HTTP 403 with 0 bytes, and the homepage serves a Cloudflare "Just a moment..." interactive challenge (HTTP 403) even through a real headless Playwright browser. Technically blocked, not a scope decision.
- **clubelo.com** — unreachable from this environment across `clubelo.com`, `www.clubelo.com`, and `api.clubelo.com` (connection timeouts, one stray 403). `robots.txt` itself is permissive when it does load, so this isn't a compliance call — the site/API appears to be down or blocking at the network level right now. Not pursued further; may be worth revisiting later.
- **AccuWeather** — see the wttr.in bullet above; hard Akamai WAF block, replaced.
- **StadiumDB** — the one candidate that survived triage; see its own bullet above.
